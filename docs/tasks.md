# remplanner-mcp — план реализации

Ссылки: архитектура — `docs/design.md`, факты о сайте — `docs/remplanner-features.md`,
отчёт разведки — `.orca-reports/01-discovery.md`. Каждая задача — отдельный небольшой коммит;
«Приёмка» — проверяемые критерии. Оценки в часах работы исполнителя-агента с проверкой.

Общие правила для всех задач: секреты из `~/.remplanner-mcp/credentials.env` не печатаются и не пишутся в файлы;
на живом сайте — только проекты `mcp-test-*` (или анонимные), удаляются в конце; не больше 30 запросов в минуту.

## Этап 0. Добор разведки — ОБЯЗАТЕЛЬНЫЕ ПЕРВЫЕ ЗАДАЧИ исполнителя (нужен браузер вне песочницы)

Не выполнены на этапе разведки: песочница сессии проектировщика не давала запустить Chrome, а запись в аккаунт
была запрещена политикой. До T1 и T1a не начинать этапы 2–3: от их результатов зависят форматы в `model/*`.

### T1a. Запись в проект аккаунта и сессии — 0,5 ч — ✅ выполнено 15.11.2026
Запустить `python3 -I scripts/probe-account-write.py`: два своих входа подряд (выбивает ли новый вход старую сессию),
копия → запись тестовой модели → GET → запись с устаревшим `save_id` и `is_forced=0` → восстановление → сверка с
`.orca-reports/backup-<OID>-before.json`. Приёмка: в выводе `FINAL data == backup: True`; в design §3 заменены
пометки «[проверить]» про одну сессию и устаревший `save_id`.
Результат: **FINAL data == backup: True**; второй вход немедленно разлогинивает первую сессию; при устаревшем
`save_id` и `is_forced=0` сервер отвечает `result:"fail"` + диалог «Сохранить все равно» и данные не пишет.
Итоги в `.orca-reports/02-feasibility.md`.

### T1. Нормализация модели редактором (анонимно) — 2 ч — ✅ выполнено 15.11.2026
Скрипт `scripts/probe-normalize.ts`: создать анонимный проект через UI (кнопка «Нарисовать чертежи своими руками»),
вызвать `$Project.restore(model)` для `tests/fixtures/anon-rect-4000x3000.json`, затем `$Project.draw({rooms:1})`,
снять `project.copy("server")` и `ROOMS2`, сделать скриншот SVG, сохранить через `project.save(false,true)`,
открыть заново в чистом контексте и снять ещё один скриншот.
Заодно снять эталоны: одну стену, дверь и окно, диван, нарисованные **руками через UI** (headed), — `project.copy`
после каждого шага.
Приёмка: `api-dump.normalize.json` и `screenshots/t1-*.png`; ответы в отчёте: (а) сохраняются ли стена, дверь и окно
из «сырой» модели без `l1/r1`; (б) находится ли комната площадью 12,00 м² по оси (**факт: 10,64 м² по внутренним
граням** = ось минус толщина; 11,4 м² было неверным ожиданием); (в) соответствие ключей каталога и `hole.type`
(`door` → `single` подтверждено кликом, `window` → `window`); (г) поля предмета после установки из UI; (д) знак угла
(по часовой стрелке, подтверждено); (е) где хранится имя помещения (`rooms2[rid].zones[0].name`, см. 02-feasibility).
Итоги: «сырая» модель требует дополнения `l1/l2/r1/r2` у стен и `p1/p2` у проёмов, после этого круг
restore → draw → save → перезагрузка проходит без потерь, комната находится (10,64 м²).

## Этап 1. Каркас

### T4. Каркас проекта — 1 ч
`package.json` (scripts: `serve`, `login`, `check`, `discover`, `test`, `test:contract`, `test:live`, `typecheck`),
`tsconfig.json` (noEmit, `allowImportingTsExtensions`), `src/config.ts`, `src/errors.ts`, README с установкой
(`NODE_OPTIONS=--use-system-ca npm install`). Приёмка: `npm run typecheck` и пустой `npm test` проходят.

### T5. Учётные данные и сессия — 1,5 ч
`credentials.ts` (парсер env-файла, проверка прав 0600 с предупреждением), `session.ts` (load/save `state.json`,
0600, проверка срока cookies). Приёмка: юнит-тесты на парсер (кавычки, комментарии, пустые строки), на маскирование
в сообщениях об ошибках (значение пароля не встречается ни в одном `Error.message`).

### T6. Браузер и вход — 2 ч
`browser.ts` (Chrome → кэш Playwright, ленивый запуск, закрытие по простою), `login.ts` (форма `/client/`, ожидание
`#clientline.is_logged`, детект капчи), `cli.ts login|check`. Приёмка: `npm run login` создаёт `state.json`;
`npm run check` печатает `logged_in: true`, тариф и число проектов; при неверном пароле — `AUTH_FAILED`.

### T7. HTTP-клиент и API — 2 ч
`http.ts` (cookies из state, таймауты, ограничитель частоты, детект `reload:101` → `SESSION_EXPIRED` → один повторный вход),
`api.ts`: `loadModel`, `saveModel` (fallback), `createAnonProject`, функции ЛК из T2.
Приёмка: юнит-тесты на разбор ответов (фикстуры ответов `load`/`save`), живой `check` читает модель тестового проекта.

## Этап 2. Модель (чистые функции, без сети)

### T8. Типы, единицы, геометрия — 2 ч
`model/types.ts`, `units.ts`, `geometry.ts` (пересечение отрезков, точка на отрезке, полигон: площадь, обход,
принадлежность точки, смещение линии). Приёмка: ≥ 30 юнит-тестов, включая вырожденные случаи.

### T9. Стены и помещения — 4 ч
`model/walls.ts`: `addWall`, `addPolyline`, `addRoomRect` (inner/axis, разные толщины сторон, общие стены с
соседней комнатой), `addRoomPolygon`, `updateWall` (длина с якорем, толщина по сторонам, перенос узла со связанными
стенами), `moveWall`, `splitWall`, `deleteWall`; генерация `link`-ов по эталонам T1.
Приёмка: прямоугольник 4000×3000 inner при толщине 200 даёт осевой контур 4200×3200; две комнаты с общей стеной не
дублируют стену; результат совпадает со структурой нормализованных фикстур T1 (без производных полей).
Факт T1: перед `$Project.restore` модель обязана содержать `l1/l2/r1/r2` (нормаль левой грани
`(dy,−dx)/len·depth/2`) — пред-/постобработка в `model/walls.ts` или `editor/adapter.ts`.

### T10. Проёмы — 2 ч
`model/openings.ts`: таблица «тип каталога → `hole.type`/`group`/дефолты» из T1 (проверено: `door` → `single`,
`window` → `window`); `offset`/`from`/`center`, направление открывания, подоконник, арка, наличники; проверки
коллизий.
Приёмка: дверь 800 с отступом 300 от угла внутренней грани даёт `pc` в нужной точке оси (тест); пересекающиеся
проёмы → `GEOMETRY_CONFLICT`.
Факт T1: у проёмов в модели, отдаваемой в `$Project.restore`, обязательны `p1/p2` (края на оси стены,
`pc ± width/2`), иначе редактор молча удаляет окно/дверь.

### T11. Каталог — 1,5 ч
`catalog.ts`: загрузка `global_tools` из бандла (имя файла берётся со страницы редактора), кэш по `global_version`,
поиск (нормализация регистра и ё/е, совпадение по `title`, `name`, `group`), фильтры. Приёмка: «диван» находит
диваны, «унитаз» — `toilet`; размеры отдаются в мм; офлайн-тест на сохранённом снимке каталога
`tests/fixtures/catalog-sample.json` (50 позиций).

### T12. Предметы — 2 ч
`model/items.ts`: `addItem` (center / against_wall / in_room+corner), `updateItem`, `deleteItem`, проверка
«внутри помещения» по полигонам комнат из нормализованной модели. Приёмка: диван у стены с `gap_mm=0` касается
внутренней грани (тест); точка вне комнат → `OUTSIDE_ROOM`.

### T13. Компактная модель и валидация — 2 ч
`model/compact.ts` (метки W/R/O/I, длины по внутренним граням, площади), `model/validate.ts` (инварианты из design §3).
Приёмка: компактное представление фикстуры 4000×3000 меньше 2 КБ и содержит площадь 12,00 м²; валидатор ловит
5 подготовленных «сломанных» фикстур.

## Этап 3. Редактор (B)

### T14. Адаптер редактора — 3 ч

`save()` через `project.save(false,true)` с ожиданием ответа `/setup/api/planner/save/`; сравнение до и после
нормализации (удалённые id → `NORMALIZATION_DROPPED`). Приёмка: контрактный тест (`npm run test:contract`, анонимно)
проходит; время нормализации маленького проекта < 2 с.
Факты T1: цепочка restore → draw → save в headless проверена; перед restore добавлять `l1/l2/r1/r2` и `p1/p2`
проёмов; каноническое чтение — GET-модель (save пишет больше, чем `copy("server")`); id комнат (`ROOMS1/ROOMS2`)
перегенерируются — не использовать как стабильные; оверлеи `#planner_ui_message_fog` и `.planner_ui_message`
