# remplanner-mcp — план фазы 2

Ссылки: проект — [phase2-design.md](phase2-design.md), карта покрытия — [coverage.md](coverage.md), отчёт разведки —
`.orca-reports/15-phase2-research.md`. Нумерация `F2-NN`, чтобы не пересекаться с `T*` в [tasks.md](tasks.md).
Общие правила — как в tasks.md: одна задача — один коммит; секреты не печатаются; на живом сайте — только анонимные
проекты; ≤ 30 запросов в минуту, сохранение не чаще раза в 5 с. **PRO-сущности в модель бесплатного или анонимного
проекта не записываются** — ни в пробах, ни в тестах (AGENTS.md, правило 5).

Оценки — часы работы исполнителя-агента с проверкой.

## Этап 0. Эталоны (браузер вне песочницы)

### F2-01. Съём эталонов из UI по каждому новому типу сущности — 3 ч
Скрипт `scripts/probes/phase2-ui-refs.ts` (готов, не запускался): анонимный проект, база «коридор + 3 комнаты»
(та же геометрия, что T24: оси x∈[0,600], y∈[−300,120], коридор y=0, перегородки x=300 и x=500, толщина 20 см),
затем сценарии мышью через инструменты UI. После каждого сценария — `project.copy("server")`, разница по коллекциям,
скриншот; в конце — save → reload → проверка, что созданные id на месте.

Запуск: `node scripts/probes/phase2-ui-refs.ts [--headed] [--only=S05,S13]`. Вывод: `.orca-reports/phase2-ui-refs/`
(`summary.json`, `<сценарий>.json`, `<сценарий>.png`, `final-model.json`), всё вне git.

Сценарии (координаты — см модели; «комната A» — x∈[10,290], y∈[−290,−10]; «коридор» — y∈[10,110]):

| № | Лист | Действие в UI | Что зафиксировать |
|---|---|---|---|
| S00 | init | дверь `door` на стене коридора y=0 при x=150 (клик по стене) | базовый проём для S03, S08 |
| S01 | break_walls | `break`, клик по перегородке x=500 | `walls[id].demount`, `p*.demount`, судьба `sectors` |
| S02 | break_walls | `break_part`, протяжка по верхней стене y=−300 от x=50 до x=150 | `sectors[sid]` (`pc`, `width`), появились ли дочерние стены |
| S03 | break_walls | `break_door`, клик по двери из S00 | `holes[hid].demount` |
| S04 | break_walls | `remove_break`, клик по стене из S01 | что обнуляется |
| S05 | create_walls | `wall_create_gypsum`, протяжка в комнате A от (150,−290) до (150,−10) | `plan:"c"`, **код материала** (`c_*`), толщина по умолчанию, связи |
| S05b | create_walls | то же для `wall_create_pgb`, `wall_create_blocks`, `wall_create_bricks` | коды материалов |

| S10 | waterplan | `waterspot_cold_hot` на стене x=290 комнаты A (клик у грани при y=−150); ПКМ → высота 60 см | `items`: `name`, `pc` относительно грани, `angle`, `over_floor`, группа |
| S11 | waterplan | `waterspot_drainage_cold_hot` рядом с S10; ПКМ → высота канализации 30 см | поле высоты канализации |
| S12 | sockets | `socket`, клик у грани стены y=−300 комнаты A при x=100 | `socket_group`, `pc`, `angle`, `id_wall`, `wall_direction`, `over_floor` |
| S13 | sockets | второй `socket` вплотную к S12 (группа), третий — над S12 с отводом курсора от стены (второй контур) | формат группы, `layer` |
| S14 | sockets | `wire_light` на стене коридора; `electric_shield` на стене x=0 коридора | выводы и щиток как предметы |
| S15 | light_connections | `light_switch_double` у двери S00 со стороны коридора | выключатель (клавиши) |
| S16 | light | `chandelier` в центре комнаты A; `lightspot` в коридоре; `bra` на стене комнаты A | потолочные и настенные светильники, признак «по центру» |
| S17 | rooms | ПКМ по маркеру площади комнаты A → имя «Спальня», цвет фона | `zones[i].name`, `color` |
| S18 | floor | `laminate`, клик в комнате A; ПКМ → подъём пола 5 см, размер плашки 120×20 | `floors[i]`: `cover`, `f0offset`, `width`, `height`, `type_laying` |
| S19 | floor | `floor_tile`, клик в коридоре; ПКМ → укладка «ёлочка» или по диагонали | значения `type_laying`, `angle` |

| S24 | init | «Добавить размер» (нижняя панель), протяжка от (10,−290) до (290,−290); ПКМ → «на всех листах» | `rulers[]` (`p*_target`, `offset`, `plan`, `show_everywhere`) |

PRO-инструменты (трубы, кабели, связи выключателей, комментарии, плинтусы, зоны пола и потолка) сценарий **не кликает**:
он проверяет класс `is_pro` у кнопки и записывает в `summary.json` `blocked: "pro"`. Так же фиксируется полный список
PRO-ключей текущей сессии (`pro_keys`).

Приёмка: в `summary.json` для каждого сценария `ok: true` или причина; для S01–S24 есть JSON с изменёнными
коллекциями; после save → reload все созданные id на месте (`roundtrip.missing = []`). По итогам исполнитель кладёт
обезличенные фикстуры `tests/fixtures/ui-ref-p2-<тема>.json` с `_source` (тема: `demolition`, `partitions`, `zones`,
`waterspots`, `risers`, `sockets`, `switches`, `lights`, `rooms`, `floor`, `ceiling`, `walls`, `rulers`).
Если сценарий не воспроизводится мышью (магниты, меню), в отчёте — шаги для ручного съёма в headed-режиме.

### F2-02. Круг restore → save → reload и прямые правки — 1,5 ч — зависит от F2-01
Скрипт `scripts/probes/phase2-restore-check.ts` (готов, не запускался). В новом анонимном проекте:
(а) restore `final-model.json` из F2-01 → draw → copy → save → reload — счётчики коллекций и поля отделки совпадают;
(б) правки «как Node» на нормализованной базе: `rooms2[rid].floors[i]` (`exist, cover, f0offset`), `ceilings[i]`
(`exist, type, level`), `zones[i].name`, `walls[id].demount=1`, `sectors`, `holes[].demount`, розетка из эталона S12
с другим `pc` вдоль той же грани, размер из S24 — после normalize поля на месте, `id_wall` у розетки пересчитан,
комнаты и их id не изменились; (в) смена геометрии (сдвиг перегородки на 20 см) после отделки — что осталось
(`FINISH_RESET`). Вывод: `.orca-reports/phase2-restore-check.json`.
Приёмка: ответы (а)–(в) в отчёте; решение «Node-патч или методы редактора» для каждого типа (пол, потолок, стены,
розетки, графы) записано в phase2-design §2.

## Этап 1. Общее

### F2-03. Тариф: список PRO-ключей и проверка до мутации — 1,5 ч — зависит от F2-01
`inject.js` читает `#plannertool_*.is_pro` и PRO-кнопки нижней панели; кеш по `global_version`; `toolkit` проверяет
ключ до мутации → `NOT_AVAILABLE_ON_TARIFF{tool,key}`. Приёмка: юнит на mock DOM (ключ `water_pipe` отклонён,
`socket` принят); `editor_status` показывает число PRO-ключей.

### F2-04. Чтение: разделы model_get и проверки model_validate — 2 ч — зависит от F2-02
Разделы `demolition`, `partitions`, `fixtures`, `networks`, `finishes`, `annotations` в компактной модели; проверки
phase2-design §3.4. Приёмка: юнит на фикстурах F2-01 (числа: расстояние розетки S12 до угла, подъём пола S18,
опуск S20 — из эталона).

## Этап 2. Перепланировка

### F2-05. Демонтаж — 2,5 ч — зависит от F2-02
`model/demolition.ts` + `demolish`, `demolish_cancel`. Приёмка: юнит — стена, участок (центр и ширина сектора равны
эталону S02 при тех же входных мм), проём, предмет; атомарность; живой анонимный сценарий «демонтаж перегородки +
участка» → `render_plan break_walls` → save → reload → поля на месте.

### F2-06. Перегородки, ГКЛ-короб, зонирование, замена проёма — 3,5 ч — зависит от F2-02, F2-05
`material` у `wall_add kind=partition` (коды из S05), несущие листа `c` с учётом демонтажа, `pillar_add kind`,
`zone_line_add kind=room`, `opening_add replaces`. Приёмка: юнит; живой сценарий «снести перегородку x=500, поставить
ГКЛ-перегородку x=450, зонировать коридор» → площади зон из редактора = (длины по осям − толщины) по формуле рядом
с тестом; `render_plan create_walls`.

## Этап 3. Точки и сети

### F2-07. fixture_add: точки на стене и в помещении — 4 ч — зависит от F2-02, F2-03
`model/fixtures.ts`: offset → центр на внутренней грани, угол, сторона; группы и контуры по S13; `room_center`;
листы из каталога. Расширение `item_update` (перемещение вдоль стены, высота). Приёмка: юнит — центр розетки S12
при тех же входных мм совпадает с эталоном ±0,1 мм, `angle` совпадает; живой сценарий «2 розетки группой, выключатель,
вывод под свет, люстра по центру, выводы воды ХВС+ГВС+канализация» → после normalize у всех настенных точек `id_wall`
не пуст → `render_plan sockets|light_connections|light|waterplan`.

### F2-08. Стояки и ввод воды — 1 ч — зависит от F2-07
`fixture_add` для `items_on_walls` исходного плана (`water*`, `drainage_column`, `ceiling_water`). Приёмка: юнит
по S09; живой — стояк в углу комнаты, `render_plan init`.

### F2-09. network_add: трубы, кабели, связи выключателей — 4 ч — **только при PRO-аккаунте**, зависит от F2-07
Граф `GraphLines` по эталонам, снятым в PRO-аккаунте (сценарии S10–S16 + трубы, кабель от щитка, связь
выключатель → люстра; съём — по правилу 3 AGENTS.md с разрешения пользователя). На бесплатном тарифе инструмент
возвращает `NOT_AVAILABLE_ON_TARIFF`, и задача сводится к этому (0,5 ч). Приёмка: юнит на эталонах; проверка в
PRO-аккаунте «копия → запись → проверка → восстановление».

## Этап 4. Отделка и подписи

### F2-10. Отделка: имя помещения, пол, потолок, стены — 4 ч — зависит от F2-02, F2-04
`model/finishes.ts`: поиск зоны по `room_id`/точке, правка `zones`, `floors`, `ceilings`, участки `decors` по граням
(формат S22, S23); `room_set_name`, `floor_finish_set`, `ceiling_set`, `wall_finish_set`; предупреждение `FINISH_RESET`
у мутаций стен. Приёмка: юнит на фикстурах S17–S23; живой сценарий «назвать комнату, ламинат с подъёмом 50 мм,
натяжной потолок с опуском 100 мм, покраска стен + плиточный фартук 600 мм на высоте 850 мм» → save → reload → поля на
месте → `render_plan rooms|floor|ceiling|walls`.

### F2-11. Размеры, комментарии, entity_delete, контракт фазы 2 — 2 ч — зависит от F2-03
`dimension_add`, `comment_add` (PRO-гейт), `entity_delete`. Контрактный тест: restore эталонов F2-01 → draw → copy,
инварианты (число элементов каждой коллекции, `exist` отделки, `id_wall` розеток) — падение → `EDITOR_INCOMPATIBLE`.
Приёмка: юнит; `npm run test:contract` зелёный.

### F2-12. Живой сценарий фазы 2 и документация — 2 ч — зависит от F2-05…F2-11
`tests/live/phase2.test.ts` (`REMPLANNER_LIVE=1`, анонимно): база → демонтаж → перегородка → точки → отделка → размер →
save → reload → разделы `model_get` совпадают; PNG листов в `~/.remplanner-mcp/renders/`. README и design §7: таблица
инструментов фазы 2, ограничения тарифа. Приёмка: `npm test`, `npm run typecheck`, `npm run test:live` зелёные.
