# remplanner-mcp — проект решения

Статус: черновик по итогам разведки 15.11.2026 (см. `.orca-reports/01-discovery.md`). Факты о сайте собраны в
`docs/remplanner-features.md`. Места с пометкой **[проверить]** без браузера и входа проверить не удалось;
их закрывают задачи T1–T3 из `docs/tasks.md`.

## 1. Цель и границы

MCP-сервер, через который агент (Claude Code, OpenCode, Codex) в аккаунте пользователя на remplanner.ru:
создаёт и открывает проекты, рисует стены и комнаты с точными размерами, ставит проёмы, двери, окна, мебель
и сантехнику, задаёт высоты (и отделку — во второй фазе), смотрит результат картинкой и сохраняет.

Вне границ: обход тарифных ограничений (PRO-экспорт, 3D и лимит проектов бесплатного аккаунта), обход капчи,
одновременная правка проекта человеком и агентом, публикация чего-либо наружу.

## 2. Факты, определяющие архитектуру

1. Внутренний JSON API у сайта есть: `GET /setup/api/planner/?object_id&plan_id` отдаёт модель строкой JSON,
   `POST /setup/api/planner/save/` её принимает. Сервер хранит модель **как непрозрачный блоб**: круг
   «сохранить → загрузить» вернул модель байт в байт, геометрию сервер не проверяет и не пересчитывает.
2. Модель — это сериализация клиентских объектов (`project.copy("server")`). Значительная её часть —
   **производные данные**: контуры граней стен `l1/r1/l2/r2…`, связи узлов `p*.link`, соседи, принадлежность
   комнатам (`room_on_left/right`, `id_room` у предметов), площади. Их считает JS редактора (`Wall.calc()`,
   `ROOMS2`, `ITEMS.setParents()`). При загрузке редактор **удаляет «сломанные» элементы**: стены короче 1–3 см,
   проёмы без корректных точек (`remove_broken`, `restore`).
3. В странице есть глобальное состояние и публичные функции: `window.WALLS`, `ITEMS`, `PILLARS`, `ROOMS2`,
   `$Project.restore(model)`, `$Project.draw({rooms:1})`, `project.copy("server")`, `project.save(...)`.
   Именно этой цепочкой редактор импортирует файл `.plan`, то есть это поддерживаемый самим сайтом путь.
4. 2D-план — это SVG в DOM (svg.js), поэтому картинку плана можно получить скриншотом элемента без PRO-экспорта.
5. Каталог (1616 позиций) лежит статически в `planner.tools___N___ts.js` (`window.global_tools`), с размерами в см.
6. Внутренние единицы — см. Ось Y направлена вниз (SVG).
7. Бесплатный аккаунт: **один проект**, только 2D. Анонимный проект создаётся без входа.
8. Капчи при входе нет; есть JS-ловушка для ботов (`*_trigger=1` выставляет JS страницы).

9. Аккаунт пользователя — **бесплатный, ровно один проект** (тестовый; пользователь разрешил писать в него
   с обязательной копией и восстановлением). Создание, копирование и удаление проектов на этом тарифе недоступны
   или защищены: удаление требует координат реального клика (`clear_now={clientX}-{clientY}`), копия — PRO.
10. Сессия хранится в cookies (`authcp`, `authkey`, `visitor_id`, …) со сроком около 1 года. **Проверено
    (T1a, 15.11.2026): одна активная сессия на аккаунт — второй вход немедленно разлогинивает предыдущий**
    (два входа подряд из `scripts/probe-account-write.py`).
11. Открытие проекта и чтение его модели создают на сервере новую резервную копию (было 0 → стало 1).
12. Эталон стены, нарисованной в UI, — `tests/fixtures/ui-one-wall.json`.

### Расхождения «модель из Node» (`anon-rect-4000x3000`) и «модель из UI» (`ui-one-wall`)

Проверено живыми пробами T1 (`.orca-reports/02-feasibility.md`, `api-dump.normalize*.json`):

| Поле | Наша модель | UI-модель / факт | Что делать |
|---|---|---|---|
| id | 10 символов `[a-z0-9]` | `_` + 5 символов (`_kh76n`) | перегенерация **не нужна**: id из 10 символов принимаются и переживают круг save/load |
| `p1`/`p2` | `{x,y,link}` | `{role:"p1", x, y, demount:0, bak:{x,y}}` | `role`/`demount`/`bak` **не обязательны** — restore принимает `{x,y}` и дополняет сам (у `bak` появляется `link`) |
| `l1,l2,r1,r2` | нет | есть; при направлении по +X сторона `l` = −Y (слева по ходу стены при Y вниз) | **обязательны на входе restore** (не пересчитывает!): считать самому — нормаль левой грани `(dy,−dx)/len·depth/2`; `l*f/angle/area/eds2/neighbors/room_on_*` — необязательны, редактор досчитывает |
| `holes` у проёмов | `{pc,width,height,…}` | есть `p1/p2` — края проёма на оси стены | **`p1/p2` обязательны** (`pc ± width/2` по оси), иначе `Walls.restore` молча удаляет окно/дверь |
| верхний уровень | `v, id, plan_id, walls, items, pillars, rulers, comments, total_height, final` | ещё ~45 коллекций, в том числе `rooms1`, `rooms2`, `errors{wallTooShort,wallOverWall,…}`, `drawing`, `version`, `session`, `logs`, `settings`, `params:false`, `is_forced` | базой брать загруженную модель и менять в ней только нужные коллекции; `errors` использовать в `model_validate`; каноническое чтение — GET-модель: `project.save` пишет больше, чем `copy("server")` (`borders`, `is_forced`, `params`, `logs`, `bak`; `rooms2` попадает в copy только после пересчёта комнат — этап 137 повторяет его в normalize) |
| `link` на узлах | задан вручную (`ct:node`, `z0/z1`) | у одиночной стены отсутствует | семантику `z0/z1` снять в T1 на двух соединённых стенах — **не закрыто** (см. 02-feasibility «не проверено») |

Вывод: «сырой» A-путь записи без редактора возможен только как аварийный (сервер примет что угодно); штатный путь — B.
Цепочка `restore → draw({rooms:1}) → project.save(false,true)` в headless-браузере **работает и проверена**: модель
из Node после добавления `l1/r1` и `p1/p2` проёмов проходит круг save → перезагрузка без потерь, комната находится.

## 3. Варианты и выбор

| | A. Только HTTP API | B. Состояние редактора через Playwright | C. Эмуляция мыши/клавиатуры |
|---|---|---|---|
| Чтение модели | ✔ быстро (`GET …/planner/?object_id`) | ✔ | ✘ (только картинка) |
| Запись | ✔ технически, но производные поля нужно считать самим (повторить `Wall.calc`, поиск комнат, связи) — сотни строк чужой геометрии, иначе редактор при открытии исправит или удалит элементы | ✔ редактор сам пересчитывает всё через `restore/draw`, сохраняет своим `project.save` | ✔, но точность зависит от масштаба и магнитов; стену заданной длины поставить нельзя, нужна дорисовка в меню |
| Рендер PNG | ✘ | ✔ скриншот SVG | ✔ |
| Хрупкость к смене версии сайта | средняя (формат модели) | средняя: зависим от 4–6 глобальных функций и формата | высокая (вёрстка, меню) |
| Скорость операции | ~0,2 с | 0,5–2 с (restore + draw) | секунды и десятки секунд |
| Риск испортить проект | высокий (невалидная модель сохраняется без проверки) | низкий (модель проходит через код самого редактора) | низкий |

**Выбор: гибрид «B-ядро + A-транспорт», C — только точечно.**

- Каноническая рабочая копия модели живёт в Node (TypeScript). Все операции MCP — чистые функции
  `model → model'` над JSON в формате сайта: юнит-тестируемо, детерминированно, без UI.
- После каждой мутирующей операции (или пакета операций) модель прогоняется через **адаптер редактора**
  в headless Chromium: `$Project.restore(model)` → `$Project.draw({rooms:1})` → `project.copy("server")`.
  Результат — нормализованная модель с производными полями и вычисленными комнатами; она становится новой
  канонической копией, а расхождения (элемент удалён, связь не возникла, стены пересекаются) возвращаются агенту как
  ошибки или предупреждения.
- Сохранение — штатным `project.save(false, true)` редактора (он сам выберет zip/json, ведёт `save_id`,
  обрабатывает `reload`/выход из сессии). Запасной путь — прямой `POST /save/` нормализованной модели (A).
- Чтение (`model_get`, `project_open`) — по HTTP (A) без браузера, если не нужен рендер.
- C используется только там, где нет JS-точки входа: страницы личного кабинета (создание, копирование, удаление,
  переименование проекта — если для них не найдутся AJAX-ручки, см. T2) и, возможно, отдельные PRO-функции.

Интерфейс с редактором намеренно узкий — **6 функций** (`restore`, `draw`, `copy`, `save`, чтение `global_tools`,
поиск SVG-элемента холста). Он изолирован в `src/editor/adapter.ts` и покрыт контрактным тестом
(«версия сайта ещё совместима»). Изменение `global_version` или имени бандла попадает в лог,
а несовместимость даёт ошибку `EDITOR_INCOMPATIBLE`, а не порчу проекта.

### Риски и меры

| Риск | Мера |
|---|---|
| Смена версии редактора и формата модели | контрактный тест адаптера; запоминаем `global_version` и хеши бандлов при каждом открытии; фикстуры из живых дампов; ошибка `EDITOR_INCOMPATIBLE` |
| Сохранение испорченной модели (сервер не проверяет) | писать только нормализованную редактором модель; перед сохранением инвариантный чек (стены ≥ 3 см, проёмы на стенах, нет пересечений); в ЛК есть резервные копии |
| ToS: открытого API нет, автоматизация не описана | работа только в аккаунте пользователя, частота как у человека (≤ 1 сохранения в 5 с, ≤ 30 запросов в минуту), без параллельных сессий, честный User-Agent браузера; не обходим тарифные ограничения |
| Капча или антибот | при появлении капчи (не наблюдалась) — ошибка `CAPTCHA_REQUIRED` и интерактивный `npm run login --headed`; не решаем её автоматически |
| Истечение сессии | признаки: ответ `{reload:101}`, редирект на `/client/?out=1`, пустой `data-authkey`; автоматический повторный вход из `credentials.env`, затем одна повторная попытка |
| Конфликт с открытой у пользователя вкладкой | `save_id` — оптимистичная блокировка: сравниваем перед сохранением, при расхождении — `SAVE_CONFLICT` и предложение перечитать |
| Лимит одного проекта у бесплатного аккаунта | MCP по умолчанию работает с **единственным проектом** аккаунта (`project_open` без параметров открывает его); `project_create`, `project_copy` → `NOT_AVAILABLE_ON_TARIFF`; `project_delete` не реализуется (удаление в ЛК требует реального клика). **Интеграционные тесты — только в анонимных проектах**; запись в проект аккаунта — только с копией в `backups/` и восстановлением |
| Одна сессия на аккаунт (гипотеза: вход в браузере выбивает MCP и наоборот) | автоматический повторный вход не больше 1 раза за операцию и не чаще 1 раза в 10 минут; при повторном выбивании — `SESSION_TAKEN_OVER` («аккаунт открыт в другом месте; закройте вкладку редактора или повторите позже»); вход не делаем «молча» в цикле, чтобы не выбивать пользователя |
| Перезапись ручных правок пользователя | перед каждым сохранением `GET` модели: если серверный `save_id` больше нашего или `data` не совпадает с базой нашей рабочей копии → `SAVE_CONFLICT` с diff; `is_forced=1` только для явного `project_save(force:true)`; проверено T1a: при `is_forced=0` и устаревшем `save_id` сервер отвечает `result:"fail"` + `html_code` с диалогом «проект сохранён в другой вкладке… Сохранить все равно» (кнопка `save_project_from_fog`) и **данные не пишет** — это и есть серверная сторона `SAVE_CONFLICT` |

## 4. Стек и структура

- Node.js ≥ 22.18, TypeScript без сборки (type stripping), ESM — как в boss-mcp.
- `@modelcontextprotocol/sdk` (stdio), `zod` (схемы входа), `playwright-core` (системный Chrome или кэш Playwright).
- Без других рантайм-зависимостей; геометрия пишется своя (отрезки, полигоны, проекции).

```
src/
  cli.ts            # serve | login | check | discover
  config.ts         # пути (~/.remplanner-mcp), BASE_URL, лимиты, таймауты
  credentials.ts    # чтение credentials.env (0600), без логирования значений
  session.ts        # state.json (cookies + localStorage), проверка срока
  login.ts          # вход: HTTP-форма или Playwright; детект капчи
  http.ts           # fetch с cookie, таймаутами, ретраями, детектом reload:101
  api.ts            # A: loadModel, saveModel, createAnon, projects (ЛК), floors/plans
  browser.ts        # запуск Chrome/кэша, общий BrowserContext
  editor/
    adapter.ts      # B: открыть проект, restore/draw/copy/save, screenshot
    inject.js       # функции, исполняемые в странице (page.evaluate)
    compat.ts       # версия сайта, хеши бандлов, контрактный чек
  model/
    types.ts        # типы модели remplanner (стена, проём, предмет, …)
    units.ts        # мм ⇄ см, округление до 0,1 мм
    geometry.ts     # точки, отрезки, полигоны, пересечения
    walls.ts        # операции над стенами (добавить, ломаная, комната, правка, удаление)
    openings.ts     # проёмы
    items.ts        # мебель и объекты каталога
    rooms.ts        # чтение вычисленных комнат, имена, высота
    compact.ts      # компактное представление модели для агента
    validate.ts     # инварианты перед сохранением
  catalog.ts        # загрузка и кэш global_tools, поиск (рус./англ., группа, лист)
  workspace.ts      # открытые проекты: каноническая модель, история (undo), dirty, save_id
  errors.ts         # McpError с кодами
  server.ts         # регистрация MCP-инструментов
scripts/discover.ts # разведка (сеть, глобалы, скриншоты)
tests/              # node --test
  fixtures/         # обезличенные живые дампы моделей
```

Файлы пользователя: `~/.remplanner-mcp/credentials.env` (0600, создаёт пользователь),
`~/.remplanner-mcp/state.json` (0600, cookies), `~/.remplanner-mcp/cache/catalog-<global_version>.json`,
`~/.remplanner-mcp/renders/*.png`, `~/.remplanner-mcp/backups/<object_id>/<ts>.plan.json` (снимок перед каждым сохранением).

## 5. Аутентификация и сессия

1. `npm run login` (или автоматически при первом вызове): читает `REMPLANNER_LOGIN` и `REMPLANNER_PASSWORD`
   из `credentials.env`, открывает `/client/` в браузере (headless; с `--headed` — видимый), заполняет форму
   и ждёт появления `#clientline.is_logged`. Сохраняет `storageState` в `state.json` (0600).
   Через браузер, а не через `curl`-POST: так JS страницы сам выставляет `auth_trigger` и мы не имитируем антибот-поле.
2. Каждый HTTP-запрос идёт с cookies из `state.json`; редактор открывается в контексте с тем же `storageState`.
3. Признаки протухшей сессии: `reload:101` в ответах API, редирект на `/client/?out=1`, нет `is_logged`
   на `/client/`, пустой `data-authkey` у редактора. Реакция: один автоматический повторный вход, затем повтор
   операции; при неудаче — `AUTH_FAILED` с подсказкой.
4. Признаки капчи (`captcha` в DOM формы, HTTP 403/429 на `/client/`) → `CAPTCHA_REQUIRED`, без автоматического решения.
5. Режим `REMPLANNER_ANON=1` (для тестов и демо): без входа, проекты создаются анонимно (`/planner/create/`),
   доступ к ним — по cookie `visitor_id` в `state.anon.json`.

Значения логина и пароля нигде не логируются и не попадают в ошибки и дампы; в логах — только `login=***`.

## 6. Система координат и единицы в инструментах

- Все длины во входах и выходах инструментов — **миллиметры** (целые или с одним знаком после запятой).
  Внутри: см = мм / 10, точность хранения 0,1 мм.
- Система координат плана: начало в произвольной точке, **X вправо, Y вниз** (как на экране редактора).
  Углы — градусы, **по часовой стрелке** от оси X (проверено T1 на стенах, нарисованных мышью:
  +X → 0°, +Y вниз → +90°, −X → 179°, −Y вверх → −91°).
- Стена задаётся **осевой линией** и толщиной. Для удобства у `room_add_rect` и `room_add_polygon` есть
  `dimensions: "inner"` (по умолчанию: размеры — чистые внутренние размеры помещения, как у пользователя в замерах)
  или `"axis"`.
- Проём на стене задаётся смещением от начала стены (`p1`) до ближайшего края проёма вдоль оси (`offset_mm`)
  либо от выбранного угла помещения (`from: "start" | "end"`).
- Идентификаторы — родные id сайта (10 символов `[a-z0-9]`); в компактной модели у стен ещё есть
  человекочитаемые метки (`W1…`, `R1…`), стабильные в рамках сессии.

## 7. MCP-инструменты

Общие правила: мутирующие инструменты меняют рабочую копию открытого проекта и **не сохраняют** на сервер,
пока не вызван `project_save` (или не передан `autosave: true`). Каждая мутация возвращает краткий diff и
предупреждения нормализации. `project` — необязательный параметр (по умолчанию — последний открытый проект).

### 7.1 Сессия и проекты

| Инструмент | Параметры | Результат / примечания |
|---|---|---|
| `auth_status` | — | `{logged_in, account_email_masked, tariff: free\|pro\|unknown, projects_limit, mode: account\|anon}` |
| `project_list` | — | `[{object_id, title, updated_at, floors, plans}]`, разбор HTML `/client/` (`tr#object{id}`) |
| `project_create` | `title` (по умолчанию `mcp-…`), `units?: cm\|mm` | `{object_id, plan_id}`; `PLAN_LIMIT` у бесплатного аккаунта, если проект уже есть |
| `project_open` | `object_id`, `plan_id?` (по умолчанию — основной), `floor?` | загружает модель (A), возвращает компактную модель |
| `project_copy` | `object_id`, `title` | PRO; иначе `NOT_AVAILABLE_ON_TARIFF` |
| `project_rename` | `object_id`, `title` (≤ 40 символов) | `POST /client/ajax/object_edit_name/` (`object_id`, `name`) |

## 9. Как агент проверяет результат

1. Каждая мутация возвращает diff и предупреждения нормализации (например, «стена W3 соединена с W4 узлом»).
2. `model_get` (compact) — числовая проверка: длины стен по внутренним граням, площади комнат, отступы проёмов.
3. `model_validate` — инварианты.
4. `render_plan` — визуальная проверка (размеры включены), PNG сразу в ответе инструмента.
5. После `project_save` можно вызвать `project_open` с `fresh: true`: перечитывает модель с сервера по HTTP
   и сравнивает её с рабочей копией (`roundtrip_ok`).

Рекомендуемый сценарий в описании инструментов: «нарисовал → `model_validate` → `render_plan` → `project_save`».

## 12. Топология стен

Раздел написан на этапе 10 (`.orca-reports/10-topology-design.md`). Он отвечает на вопрос, можно ли поручить
редактору связи стен, грани, T-примыкания и комнаты, чтобы Node задавал только намерение. Повод — находки
R2-2…R2-7 и R2-14 (`.orca-reports/09-review-round2.md`): самодельная топология в `src/model/walls.ts` и
`items.ts` даёт всё новые ошибки, а сценарий «коридор и три комнаты» (R2-4) отклоняется с `UNSUPPORTED_JUNCTION`.

### 12.1 Что делает редактор (прочитано в бандле `app.3.0___683___1794385633.min.js`, global_version 757)

Пометки: **[код]** — прочитано в бандле; **[проверить]** — нужна живая проба T24
(`scripts/probes/editor-api.ts`).

- **Связи редактор выводит из геометрии при каждом пересчёте [код].** `$Project.draw(e)` → `calcPlan(e)` →
  `$Project.calc()` = `WALLS.calc1() → calc2() → calc3() → calc4()`. Здесь:
  - `Wall.calc2()` вызывает `link1()`: удаляет `p1.link`/`p2.link` стены и ставит `node`-связь, если конец
    совпадает с концом другой стены в пределах **1,5 см** (и угол между стенами 3…177° или толщины равны);
  - `Wall.calc3()` вызывает `link2()`: свободному концу ставит `edge`-связь (`z0: l|r|s|e`), если он лежит на грани
    `eds.l`/`eds.r` (торце `eds.s`/`eds.e`) другой стены в пределах **1 см** и стена уходит от этой грани
    (угол 5…175°);
  - `calc4()` строит грани с учётом соседей (`getPts1/getPts2/getEds2`), длины `length_l/length_r` и площади.

  Итог: поля `link` во входной модели (и в модели после `$Project.restore`) при draw **перезаписываются** геометрией.
  Связи Node не нужны совсем, нужно только правильно поставить концы.
- **Как выглядит T-примыкание [код + эталон UI].** Конец примыкающей стены лежит **на грани** несущей стены
  (ось несущей ± depth/2), а не на её оси. Несущую стену редактор **не режет**: у неё остаётся одна стена,
  её грань делится на участки в `eds2`. Эталон мыши `tests/fixtures/ui-ref-two-rooms.json` это подтверждает:
  `_50415.p1 = (199.9, −150)` при оси соседа x≈195 и толщине 10 → `edge`, `z0:"l"`. Угол, замыкающий контур,
  мышь тоже часто делает `edge` на грань, а не `node`.
- **Комнаты [код].** `calcPlan(e)` с `e.rooms=1` вызывает `ROOMS2.get()` (на листе `ab` — `ROOMS1.get()`). Комнаты
  находятся по граням стен, T-узлы обрабатываются штатно.
- **Инструмент «Нарисовать стену» [код].** Класс `WallCursor`:
  - `down` создаёт стену `WALLS[id] = new Wall({id,p1,p2,depth,plan,role,material,color})` и привязывает начало
    к линии привязки `link_using_baseline("p1", refline1, zone)`;
  - `move` двигает `p2` с магнитами (`getConnection2`, `magnetToAxis…`);
  - `up` проверяет стену (`is_too_short`, `hasClosestAndParallelWall`, `isOverObject`), вызывает `merge()`
    (сливает коллинеарное продолжение той же толщины и материала) и `$Project.draw({rooms:1})`.

  Вся интерактивная часть (refline, «зоны», направления `pl/pr`) нужна только для привязки к курсору.
  При точных координатах её заменяют `link1/link2` внутри draw.
- **Другие точки входа [код]:**
  - `Wall.split(point)` режет стену: раздаёт проёмы по `pc`, переносит связь `p2` и входящие `edge`-ссылки;
  - `Wall.merge()` сливает стены;
  - `rebuildNodeConnectedWalls()` и `rebuildEdgeConnectedWalls()` после перемещения стены переносят концы соседей
    в общий узел или на новую грань;
  - `isOverWall()`/`isOverObject()` проверяют наложения;
  - `Walls.remove_broken()` удаляет стены короче 1 см или без точек;
  - `Walls.restore()` удаляет стены короче 3 см.

  Функций `Walls.add`, `WALLS.create`, `attach`, `connect` в бандле нет.
- **Мышь точных размеров не даёт.** В эталоне координаты 194,9…199,9 вместо 200. Длину правят потом стрелками
  с шагом 1 мм или в меню, поэтому эмуляция мыши (вариант C) отклонена.

### 12.2 Вердикт

**Гипотеза подтверждается по коду в усиленном виде [проверить T24].** Эмулировать мышь или вызывать
`WallCursor` не нужно. Достаточно отдать редактору **точную геометрию** (оси, толщина; T-концы на грани)
через уже используемые `restore → draw`. Связи, грани и комнаты он пересчитает сам (`link1/link2/calc4/ROOMS2.get`).
Размеры остаются точными: координаты задаёт Node в см с дробной частью, а редактор их не округляет
и не сдвигает. При draw он двигает только `l*/r*`, не `p1/p2` [проверить T24: сценарии A и B, площади до 0,01 м²].

Выбранный вариант **G — «геометрия в Node, топология в редакторе»**:

- Node отвечает за перевод намерения в отрезки:
  - мм → см, inner → axis;
  - общие стены соседних комнат: на оси уже есть стена → недостающая часть стороны находится вычитанием
    отрезков на одной прямой;
  - конец, попадающий в тело существующей стены, ставится на её ближнюю грань (T-примыкание);
  - конец, совпадающий с узлом, ставится точно в узел.
- Node **не пишет `link`**, не считает грани и комнаты. Грани `l1..r2` перед restore остаются простыми
  (ось ± depth/2), как в `prepareWallFaces`: restore их требует, draw всё равно пересчитает.
- Редактор после каждой мутации стен (через `normalize`) строит связи, грани и комнаты. Нормализованная модель
  становится канонической, и все чтения (`rooms_list`, `model_summary`, выбор стены для проёма) идут по ней.

Альтернатива **E — «операции в редакторе»** (вызывать из `page.evaluate` методы `new Wall`, `split`,
`rebuild*ConnectedWalls`, `merge`) отклонена как основная. Она расширяет контракт с 6 до ~12 внутренних методов,
и каждая операция требует живой страницы. В E есть смысл только как запасной путь для `split`, если T24 покажет,
что геометрический разрез теряет проёмы.

### 12.3 Правила геометрии в Node (замена топологии)

1. **Узел.** Концы двух стен в одной точке (допуск Node 0,01 см) редактор свяжет `node`. Концы на расстоянии
   0,01…1,5 см — ошибка `INVALID_GEOMETRY`: иначе редактор молча склеит их. Это точный размер, а не магнит.
2. **T-примыкание.** Конец новой стены внутри тела другой стены (расстояние до оси < depth/2, проекция внутри
   отрезка) ставится на ближнюю грань: `проекция ± depth/2 · нормаль`. Конец на оси несущей стены не допускается:
   редактор не даст `edge`-связь и посчитает наложение [проверить T24, сценарий C].
3. **Общая стена.** Сторону новой комнаты, лежащую на оси существующей стены той же толщины, Node урезает
   вычитанием покрытых интервалов: строятся только непокрытые куски, их концы — по правилам 1–2.
   Сторона на оси стены другой толщины → `INVALID_GEOMETRY` (смена толщины по стене не поддерживается).
   Так закрываются R2-2 (проверяется поперечное расстояние), R2-4 (коридор + 3 комнаты: стена коридора одна,
   перегородки примыкают T) и R2-14.
4. **X-пересечение** двух стен посреди отрезков → `UNSUPPORTED_JUNCTION`, отказ атомарный. Этот случай
   в квартирах редок; разрез в точке пересечения — фаза 2.
5. **Перемещение и изменение стены** (`wall_move`, `wall_update` start/end). Node двигает концы стен:
   - стоящие в том же узле — в новую точку узла;
   - примыкающие T к этой стене (`edge`-связь с `id` этой стены в последней нормализованной модели) — продлевает
     или укорачивает вдоль их оси до пересечения с новой гранью (формула та же, что
     в `rebuildEdgeConnectedWalls`);
   - проёмы каждой затронутой стены пересчитываются по расстоянию от неподвижного конца (R2-5, R2-6).
6. **Разрез** (`wall_split`) — две стены в одной точке оси с раздачей проёмов по `pc`. Входящие T-связи
   редактор переназначит сам.
7. **Атомарность** (R2-3): операция выполняется на клоне модели. Ошибка правил 1–4 или проверки после
   нормализации оставляет рабочую копию нетронутой.

### 12.4 Проверка результата редактором

`normalize` возвращает вдобавок к копии:
- связи концов (`ct`, `id`, `z0`);
- признак `isOverWall()` каждой стены;
- `errors` из `copy("server")` (`wallOverWall`, `wallTooShort`, `wallNoPointS/E`, `roomRebuild`);
- площади комнат (`ROOMS2[*].polygon`).

Workspace отклоняет мутацию (откат клона) с `INVALID_GEOMETRY`, если:
- после draw у стены `isOverWall()`;
- выросли счётчики `errors`.

Свободные (несоединённые) концы стен — штатная механика редактора (стандарт
remplanner: FAQ 2.1, отчёт 132 часть 1 — свободностоящие перегородки `plan:"c"`
и стены `plan:"a"` save сохраняет без потерь). Новые концы без связи, появившиеся
после нормализации (сравнение с диагностикой рабочей модели до операции;
унаследованные висячие концы старых проектов штатные операции не блокируют —
ревью 108 R10), дают предупреждение `wall_free_ends` со списком концов в мм,
а не отказ (142); помещение образует только замкнутый контур.

### 12.5 Влияние на слои

- **`src/model/walls.ts`.**
  - Удаляются: `linkFor`, `connectNode`, `linkedNodePoint`, `tryReuseWall`, `collinearOverlap`,
    `trimToSharedFaces`, `setNode` в части связей, а также вся логика `edge`/`node`-связей в `addRoomRect`,

  - Остаются и упрощаются: `makeWall`, `addWall`, `addPolyline`, `addRoomRect/Polygon` (правила 1–4),
    `moveWall/updateWall` (правило 5), `splitWall`, `deleteWall`, `prepareWallFaces`, `prepareForRestore`
    (связи больше не пишутся; при restore их стирать не обязательно).
  - Ожидаемо −250…−300 строк из 644.
- **`src/model/items.ts`.** Удаляются `wallCycles` и `roomPolygons` (≈ 200 строк; R2-7 исчезает вместе с ними).
  Комнаты берутся из нормализованной модели (`rooms2[*].polygon` и площадь редактора).
  `addItem` с `room` и `normalizePosition` в `tools-plan.ts` используют кеш комнат workspace.
- **`src/model/validate.ts`, `compact.ts`.** Площади и комнаты читаются из `rooms2` модели, а не из `roomPolygons`.
  Проверки «дубль оси», «no_rooms» остаются как быстрые офлайн-эвристики.
- **`src/workspace.ts`.** Мутация стен = клон → правило Node → `normalize` → проверки §12.4 → замена канонической
  копии. Нормализация вызывается после каждой мутации стен, а не только при `save`. Цена — 0,5–2 с на операцию;
  пакет из нескольких операций (`walls_add_polyline`, `room_add_rect`) нормализуется один раз.
  В офлайн-режиме (`REMPLANNER_OFFLINE_FIXTURE`) стены меняются без нормализации, комнаты и связи не обновляются.
  Инструмент сообщает это предупреждением `EDITOR_REQUIRED_FOR_ROOMS`.
- **Пересчёт комнат в normalize (этап 137).** Редактор перестраивает `rooms2` только внутри штатного сохранения
  (в начале `project.save`: план «a» → `copyRooms1` → план «c» → `draw({rooms:1})`), поэтому `copy("server")` после
  простого `draw` несёт старые комнаты — строгая сверка комнат после save (#17) давала ложный `SITE_ERROR` на каждом
  save с делением/слиянием/переносом комнаты. `normalize` повторяет ту же последовательность тех же функций редактора
  и возвращает копию с перестроенными комнатами (эталоны `tests/fixtures/ui-ref-rooms-save-*.json`).
- **Инструменты MCP.** Сигнатуры §7.2 не меняются. Меняются ответы:
  - `room_add_rect` возвращает созданные и использованные (общие) стены и комнаты из редактора;
  - `rooms_list` — только из редактора;
  - исчезает подсказка `wall_split` у `UNSUPPORTED_JUNCTION`.
- **Совместимость (T15).** Контракт адаптера пополняется неявной зависимостью: draw пересчитывает связи из
  геометрии. Её проверяет контрактный тест «коридор + 3 комнаты из модели без link → 4 комнаты, ожидаемые площади,
  T-концы получили `edge`». В `compatInfo.present` добавляются проверки
  `typeof Wall.prototype.link1/link2/calc === "function"`. Если редактор сменит правило (например, начнёт резать
  несущую стену в T-узле), упадёт контрактный тест, а рабочий путь вернёт `INVALID_GEOMETRY` по §12.4,
  а не испортит проект: потерянная связь или наложение отклоняются до сохранения.
- **Тесты.**
  - Юнит: правила 1–7 на чистых функциях (координаты концов, вычитание интервалов, атомарность, проёмы соседей).
    Тесты на `link` и `wallCycles` (`review-junctions`, часть `review-walls-fixes`) удаляются или переписываются
    на координаты.
  - Контракт: сценарий T24 становится постоянным тестом.
  - Live: коридор + 3 комнаты → save → reload.

### 12.6 Если T24 опровергнет гипотезу

Минимальный путь в текущем подходе (≈ 12 ч):
- R2-2 — поперечное расстояние в `collinearOverlap` (0,5 ч);
- R2-3 — клон и замена только при успехе (1 ч);
- R2-4 — вычитание интервалов и T-концы на грань с `edge`-связью без разреза несущей (4 ч);
- R2-5 — перенос входящих `node`/`edge`-концов при move/update/split (3 ч);
- R2-6 — пересчёт проёмов соседей (1 ч);
- R2-7 — толщина ребра контура по `wallId` (1,5 ч);
- R2-14 — эталон из T24, сценарий M (1 ч).

Правила 2–3 из §12.3 нужны в обоих вариантах, поэтому они идут первыми (T26).
