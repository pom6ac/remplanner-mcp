# CONTRIBUTING — процесс разработки MCP к веб-сервису без API

Процесс один для человека и для агентов (Claude Code, OpenCode, Codex). Он не привязан к конкретному сервису:
следующий MCP к другому сайту делается по нему же, достаточно скопировать `AGENTS.md`, этот файл,
`docs/roles/` и `docs/templates/`, а затем заменить имя проекта, пути и команды. Жёсткие правила (секреты,
сессия, запись в аккаунт, коммиты) перечислены в [AGENTS.md](AGENTS.md), здесь они не повторяются.

## Общие соглашения

- **Каталог отчётов** — `.orca-reports/`. Он закрыт в `.gitignore` и в `.git/info/exclude` и в публичный репо
  не попадает. Там же лежат копии моделей аккаунта и cookie анонимных сессий. Если проект ведётся без
  оркестратора, можно взять имя `reports/`, но тогда его тоже нужно добавить в оба файла исключений.
- **Имя отчёта** — `NN-<тема>.md`: номер этапа по порядку и короткая тема (`01-discovery`, `02-feasibility`,
  `03-impl-stage1-2`, `04-review-stage1-2`, `05-…`, `06-review-resolution`). Отчёт пишется по шаблону
  `docs/templates/report.md`, ревью — по `review.md`, резолюция — по `resolution.md`.
- **Задача агенту** ставится по шаблону `docs/templates/task-spec.md`. В ней указаны роль, вход, разрешённые
  каталоги, запреты, критерии готовности, бюджет времени и канал отчёта.
- **Одна задача — один исполнитель в дереве.** Второго исполнителя в то же рабочее дерево не запускают.
  Ревьюер (только чтение) и автор документации (свои новые файлы) могут работать параллельно с ним.
- **Факты отдельно от гипотез.** В отчёте и design у каждого утверждения есть пометка: проверено вживую
  (чем именно), прочитано в коде или только предположено. «Не проверено» — отдельный обязательный раздел.

## Фаза 0. Подготовка

**Вход:** название сервиса, место будущей публикации (публичный GitHub или нет), доступ к аккаунту пользователя.

**Что делается:**
1. `git init -b main`, `.gitignore`: `node_modules/`, `api-dump*.json`, `*.har`, `screenshots/`, `.env*`,
   `state*.json`, `credentials*.env`, `backups/`, `cache/`, каталог отчётов.
2. Каталог отчётов добавляется в `.git/info/exclude`, чтобы правка `.gitignore` его не открыла.
3. **Git-идентичность задаётся до первого коммита:** `git config --local user.name` и `user.email` со
   значениями, под которыми репо будет опубликован. Пользователь вписывает их сам, агент значения не
   подставляет. Проверка: `git config --local user.email` не пустой, `git log --format=%ae | sort -u`.
4. Учётные данные хранятся вне репо, в `~/.<проект>/credentials.env` (каталог 0700, файл 0600). Файл создаёт
   пользователь. Агенту передают только путь. Проверка без вывода значений: `cut -d= -f1`, `stat -f %Lp`.
5. Выясняется, можно ли запустить браузер в среде агента. Если нельзя, заранее решается, кто будет выполнять
   браузерные шаги.

**Выход:** репо с `.gitignore`, локальной идентичностью и файлом учётных данных.
**Готово, когда:** `git config --local user.email` не пустой, файл учётных данных существует с правами 0600,
каталог отчётов не виден в `git status`.

**Типичные ошибки:**
- Первые коммиты ушли под глобальной (рабочей) почтой. Перед публикацией пришлось бы переписывать автора
  всей истории, а пока в том же дереве коммитит исполнитель, сделать это нельзя.
- Значение, которое пользователь вставил в чат, модель видит маской. Если подставить его в команду,
  в файл ляжет маска, и сайт ответит «недопустимый формат». Правильно создать файл с плейсхолдером
  и попросить пользователя вписать значения самому.

## Фаза 1. Разведка

**Вход:** URL сервиса, учётные данные (путь), бюджет времени. Роль — [researcher](docs/roles/researcher.md).

**Что делается:**
1. **Документация сайта:** руководство, FAQ, история обновлений → `docs/<сервис>-features.md`.
2. **Бандлы JS:** страница редактора, имена бандлов и версии, глобальные объекты, функции импорта и экспорта
   модели (`restore`, `copy`, `save`), эндпоинты в коде.
3. **Перехват сети:** XHR и fetch при открытии, сохранении и входе (`scripts/discover.ts`). Для каждого
   эндпоинта отмечается, вызван ли он вживую (✔) или найден только в коде (✘).
4. **Глобальное состояние страницы:** атрибуты `body`, глобалы модели, версия формата.
5. **Круг «сохранить → загрузить»** на тестовом объекте, по возможности в анонимном режиме: прочитать,
   записать, перечитать, сравнить.
6. **Личный кабинет:** тариф, число объектов, лимиты бесплатной версии, резервные копии, что доступно только платно.
7. **Сессии:** срок cookies, признаки истечения сессии, держит ли сервис одну сессию на аккаунт
   (проверяется двумя своими входами подряд).
8. Копия объекта пользователя делается только чтением и сохраняется в каталог отчётов.

**Выход:** `docs/<сервис>-features.md`, скрипты разведки в `scripts/`, обезличенные эталоны в `tests/fixtures/`,
отчёт `.orca-reports/01-discovery.md`.
**Готово, когда:** известны эндпоинты загрузки и сохранения (хотя бы одно вызвано вживую), формат модели,
тариф и лимиты, поведение сессии. Всё непроверенное вынесено в список с готовыми скриптами для проверки.

**Типичные ошибки:**
- Тариф проверили поздно. На бесплатном тарифе один проект, второй тестовый не создать, поэтому
  интеграционные тесты пришлось переносить в анонимный режим.
- Чтение тоже даёт побочный эффект: после открытия проекта в ЛК появилась резервная копия.
- Сессию «случайно» разорвало через 5 минут, потому что пользователь в это время был в ЛК. Это и был сигнал,
  что сервис держит одну сессию на аккаунт.
- Классификатор auto-режима одного из агентов отклонил скрипт записи в аккаунт, хотя другой агент дал
  разрешение. Запись в аккаунт поручают агенту, которому пользователь разрешил это напрямую, или пользователю через `!`.

## Фаза 2. Проектирование

**Вход:** отчёт разведки. Роль — [designer](docs/roles/designer.md).

**Что делается:**
1. Сравниваются варианты:
   - **A** — внутреннее HTTP API: быстро, но сервер может принимать «сырую» модель без проверки;
   - **B** — состояние страницы в headless-браузере через `page.evaluate`: модель нормализует код самого сервиса;
   - **C** — эмуляция кликов UI: только резерв для действий, у которых нет функции в коде.
   Выбор обосновывается фактами разведки. Допустима комбинация, например «B-ядро + A-транспорт».
2. `docs/design.md`: цель и границы, факты (с пометкой «проверено» или «гипотеза»), выбор варианта, риски
   и меры, стек и структура, сессия, единицы и система координат, MCP-инструменты, модель ошибок, как агент
   проверяет результат, стратегия тестов, подключение к агентам.
3. Таблица расхождений между моделью, собранной в коде, и моделью из UI: какие поля модельный слой обязан
   генерировать сам.
4. `docs/tasks.md`: задачи по этапам, у каждой — оценка в часах и проверяемый критерий приёмки. Этап 0 —
   задачи go/no-go.

**Выход:** `docs/design.md`, `docs/tasks.md`.
**Готово, когда:** у каждой задачи есть критерий приёмки, который можно проверить командой или живой пробой,
а главная гипотеза архитектуры записана явно и стоит первой задачей этапа 0.

**Типичные ошибки:**
- Критерий приёмки был задан «по ощущению» (площадь 11,4 м²) и оказался неверным: правильное значение
  10,64 м², по внутренним граням. Числа в критериях выводятся из эталона или из формулы, записанной рядом.
- Разделение «Node-модель» / «UI-модель» не было записано, и исполнитель придумал семантику связей стен
  по сырому входу. Формат каждой структуры, которую код пишет сам, фиксируется по эталону из UI.

## Фаза 3. Go/no-go

**Вход:** design, задачи этапа 0. Роль — [researcher](docs/roles/researcher.md) или [debugger](docs/roles/debugger.md).
Исполнителю нужен браузер вне песочницы.

**Что делается:**
1. **Главная гипотеза проверяется первой** и минимальной живой пробой, до каркаса, MCP и трат на тариф.
   Пример: «модель, собранная в коде, проходит `restore → draw → save → GET` без потерь, и редактор находит комнату».
2. Запись в аккаунт (если она нужна MVP) проверяется по схеме «копия → запись → проверка → восстановление».
   Попутно выясняются конфликт версий (`save_id`) и одна ли сессия на аккаунт.
3. Эталоны снимаются из UI: объект рисуют мышью и сохраняют дамп. Это делается после ответа на главный вопрос.
4. **Бюджет времени фиксирован.** Когда бюджет вышел, новых проб не начинают, а пишут отчёт.
   Непроверенное перечисляется списком.

**Выход:** отчёт `.orca-reports/02-feasibility.md` с вердиктом GO / NO-GO / GO с условиями, дампы (вне git),
эталоны `tests/fixtures/ui-ref-*.json` и `normalized-*.json`, правки design и tasks по фактам.
**Готово, когда:** вердикт подтверждён живым прогоном (скриншот, дамп, лог), объект пользователя совпадает с копией.

**Типичные ошибки:**
- Сервер принимал любую модель, и круг «сохранил → прочитал» по HTTP проходил, а клиентский `restore`
  молча удалял проёмы без `p1/p2` и падал без граней стен `l1/r1`. HTTP-круг ничего не доказывает про импорт
  редактором: проверка нужна через сам редактор.
- Без бюджета исследователь уходит в цепочку `dbg-*.ts` (больше двадцати проб) и не сдаёт отчёт.
- Платный тариф не покупают до вердикта. Здесь он для MVP не понадобился.

## Фаза 4. Реализация слоями

**Вход:** GO, `docs/tasks.md`. Роль — [implementer](docs/roles/implementer.md).

**Что делается:**
1. **Базовый коммит разведки** — первым шагом. До него индекс проверяется на секреты, отладочные пробы
   переносятся в `scripts/probes/` и коммитятся отдельно.
2. **Слой 1 — каркас и модель чистыми функциями:** конфиг, ошибки, учётные данные, сессия, HTTP, модельный
   слой (типы, единицы, геометрия, операции, валидация). Слой проверяется юнит-тестами и анонимными
   HTTP-вызовами и не зависит от браузера.
3. **Слой 2 — адаптер браузера:** открыть, `restore`, `draw`, `copy`, `save`, рендер. Контрактный тест.
4. **Слой 3 — MCP-инструменты:** регистрация, схемы `zod`, ошибки с кодами, smoke через SDK-клиент.
5. **Задача — коммит:** одна задача из `tasks.md` — один локальный коммит явными путями после зелёных
   `typecheck` и `test`. Сообщение: `T<N>: <что сделано>`.
6. Вход в аккаунт — один раз в конце этапа, после запроса «нужен вход» и разрешения пользователя.
   Остальные живые проверки анонимные.
7. Отступление от design фиксируется в design (или в отчёте с причиной) в том же коммите.

**Выход:** коммиты по задачам, отчёт `.orca-reports/NN-impl-<этапы>.md`: таблица «задача — статус —
коммит — чем проверено», отступления, самостоятельные решения, непроверенное.
**Готово, когда:** все задачи этапа закоммичены, `typecheck` и `test` зелёные, для каждой задачи
указан способ проверки.

**Типичные ошибки:**
- Семантику формата (связи стен `link`, плоский или вложенный формат предметов) реализовали «по смыслу»,
  без сверки с эталоном. Тесты прошли, а редактор удалял предметы при `restore`.
- Операции проверили на модели, собранной своим же кодом, но не на модели, загруженной из редактора,
  у которой нет служебных полей (`at`). Операцию нужно гонять на обоих видах входа.
- В общем дереве исполнитель закоммитил весь индекс, и туда попали файлы, которые параллельный агент
  застейджил для своего коммита. Нужен `git commit -- <пути>` и проверка `git diff --cached --name-only`.
- Ограничение частоты и повторный вход сделали «внутри вызова», а не на уровне аккаунта:
  параллельные вызовы обходили лимит.

## Фаза 5. Отладка

**Вход:** падающий живой сценарий или непонятное поведение сервиса. Роль — [debugger](docs/roles/debugger.md).

**Что делается:**
1. Пробы пишутся в `scripts/probes/<тема>.ts`: одна проба — один вопрос, у файла говорящее имя.
2. Дампы и скриншоты кладутся вне git (`api-dump.<тема>.json`, `screenshots/`). В фикстуру попадает только
   обезличенная выжимка с указанием источника.
3. **Эталон снимается из UI:** то же действие выполняется мышью в редакторе, и дамп сравнивается с моделью из кода.
4. **Минимальный набор полей** ищется удалением полей по одному: после каждого удаления
   `restore → draw → save → GET`, сверка числа элементов. Результат записывается в design: какие поля
   обязательны, а какие редактор досчитывает сам.
5. Сравнение до и после идёт по инвариантам (число элементов, координаты, связи, площади), а не по байтам:
   transient-id пересчитываются.
6. Найденное правило становится юнит-тестом, а проба остаётся в `scripts/probes/` как документ.

**Выход:** причина с доказательством, правило в design, тест, пункт в отчёте этапа.
**Готово, когда:** причину воспроизводит минимальная проба, а исправление проверено живым кругом.

**Типичные ошибки:**
- Повторный `restore` в той же странице без `{reset:1}` сохранял старые данные. Найти это удалось только
  живым кругом с повторным чтением с сервера.
- Оверлеи и обучающие попапы UI мешали кликам. Их снимают кодом, а не ожиданием.
- Пользователь видит окно headed-браузера на экране. Его предупреждают, чтобы он не кликал.

## Фаза 6. Тесты

**Вход:** код задачи. Роль — [tester](docs/roles/tester.md) (или implementer для своих задач).

**Уровни:**
- **Юнит** (`npm test`) — без сети: модель, геометрия, разбор ответов, ошибки, ограничение частоты.
- **Контракт** (`npm run test:contract`) — против живого редактора, в анонимном проекте. Проверяет,
  что код сервиса по-прежнему принимает нашу модель. Падение означает `EDITOR_INCOMPATIBLE`.
- **Live** (`npm run test:live`) — полный сценарий, только при флаге (`REMPLANNER_LIVE=1`), анонимно.
- **Аккаунт** — только по явной команде пользователя, по схеме «копия → запись → проверка → восстановление».

**Правила:**
1. **Фикстуры берутся только из реальных дампов.** В каждой указаны источник (`_source`: файл дампа, дата,
   версия формата сервиса) и способ обезличивания (id → 0). Синтетические «сломанные» фикстуры допустимы,
   но их происхождение тоже записывается (`broken-*.json` от такого-то эталона).
2. **Эталон — из UI, а не из своего кода.** Ожидаемое значение берётся из объекта, нарисованного в редакторе.
3. **Тест должен падать на старом коде.** Регрессионный тест сначала запускают до фикса и убеждаются, что он красный.
4. Тест проверяет свойство, а не реализацию: физический прямоугольник повёрнутого предмета, а не только центр;
   связность в обе стороны; повторную операцию; конкурентный вызов.
5. Тест ошибочного пути вызывает этот путь через `assert.throws` или `assert.rejects`. `try/catch` с
   `assert.fail` внутри ловит собственный `AssertionError`.
6. Тесты на маскирование секретов используют искусственные значения (sentinel) и проверяют сериализацию
   ошибки (`toJSON`, вывод CLI), а не только `message`.

**Выход:** тесты в `tests/…`, их число и результат в отчёте этапа.
**Готово, когда:** все уровни, применимые к задаче, зелёные, а регрессионные тесты падали на старом коде.

**Типичные ошибки (из ревью этапов 1–2):** набор из 113 зелёных тестов не поймал 2 blocker и 13 major.
Тесты писал автор кода с тем же пониманием формата. Тест связей утверждал придуманный формат, тест дивана
игнорировал поворот, лимитер проверялся только последовательно, тест маскирования был всегда зелёным,
а фикстура ответа API хранила `plan_id` строкой, хотя реальный дамп отдаёт число.

## Фаза 7. Ревью

**Вход:** закоммиченный диапазон `<база>..<sha>`. Роль — [reviewer](docs/roles/reviewer.md).

**Что делается:**
1. Ревью проводит **независимый ревьюер**: другой агент или хотя бы свежая сессия без контекста автора.
   Ревьюер только читает, код проекта не меняет и пишет единственный файл — отчёт.
2. Область фиксируется: «коммиты после `<sha>` не оценивать». Номера строк даются по `<sha>`, а не по
   меняющемуся рабочему дереву (читать через `git show <sha>:<path>`).
3. **Сверка идёт с эталонами UI** (`ui-ref-*`, `normalized-*`) и с design, а не с тестами автора.
   Каждая находка подтверждается воспроизведением: офлайн-скриптом из stdin, подменой `fetch`, расчётом.
4. Проверяется вся история git на секреты, а не только HEAD.
5. Отчёт по шаблону `docs/templates/review.md`: вердикт (approve / request changes) и таблица находок
   «№ | серьёзность | файл:строка | проблема | подтверждение | минимальное исправление».
   Серьёзность: blocker (утечка, порча данных, неверный формат), major (неверное поведение основного
   сценария), minor (неточность, слабый тест).

**Резолюция** (implementer):
1. Находки передаются исполнителю после его текущего отчёта. Исключение — blocker и major в слое, поверх
   которого он строит текущий этап: тогда он сразу коммитит текущую работу и переключается на них.
2. По каждой находке: **тест красный → фикс → тест зелёный**, коммит с номерами находок
   (`ревью №2,№3: …`).
3. Файл `.orca-reports/NN-review-resolution.md` по шаблону `resolution.md`: что изменено, коммит,
   чем проверено. Невоспроизводимые находки объясняются отдельно.
4. **Повторное ревью** диапазона фиксов выполняет тот же или другой независимый ревьюер. Цикл закрыт,
   когда вердикт approve или все оставшиеся находки minor и вынесены в задачи.

**Выход:** `.orca-reports/NN-review-<этапы>.md`, `NN-review-resolution.md`, повторное ревью.
**Готово, когда:** blocker и major закрыты, у каждого есть регрессионный тест, повторное ревью без новых blocker.

**Типичные ошибки:**
- Ревью по тестам автора подтверждает его же ошибки. Ревью по эталонам нашло неверную семантику связей.
- Ревьюер оценивал изменяющееся дерево и путал номера строк. Нужен фиксированный `<sha>`.
- Ключ доступа попадал в `Error.message` через query строки запроса. Ревью ищет секреты и в ошибках
  времени выполнения, а не только в истории.

## Фаза 8. Публикация

**Вход:** принятые этапы MVP. Роль — [releaser](docs/roles/releaser.md).

**Что делается:**
1. **История git проверяется на секреты** по всем коммитам:
   `git grep -n -I -E '<шаблоны>' $(git rev-list --all) -- . ':!package-lock.json'`. Шаблоны: email-регэксп,
   ключи сессии в query (`authkey` и `password` со знаком равенства), начало пароля (передаётся в stdin,
   не в командной строке), маркеры приватных ключей.
2. **Нет внутренних данных:** абсолютных путей домашнего каталога, номеров объектов аккаунта, имён людей,
   корпоративных названий и адресов — в коде, docs, фикстурах и сообщениях коммитов.
3. **Автор коммитов:** `git log --format='%an <%ae>' | sort -u` содержит только публичную идентичность.
   Переписывать историю (`git filter-repo` или `rebase`) можно только при остановленных исполнителях
   и с согласия пользователя.
4. **README:** назначение, требования (Node, браузер вне песочницы), установка, вход, переменные окружения,
   подключение во все три агента (Claude Code, OpenCode, Codex), ограничения тарифа и сессии, юридическая
   оговорка про частоту запросов и ToS.
5. Лицензия, `package.json` (`private`, `version`, `repository`), тег версии, release notes.
6. `push` и публикация репо — только по явной команде пользователя.

**Выход:** чистая история, README, тег, отчёт `.orca-reports/NN-release.md`.
**Готово, когда:** все проверки из пунктов 1–3 дали пустой результат, а свежий клон по README подключается
к каждому из трёх агентов.

**Типичные ошибки:** часть коммитов ушла под рабочей почтой; в design остались абсолютные пути
и номер объекта аккаунта; в фикстурах — `object_id` и `visitor_id` до обезличивания.

## Большой контекст

Если контекст агента подходит к пределу (длинная отладка, большие дампы в выводе):
1. Новых проб не начинать.
2. Закоммитить готовое явными путями. Незаконченное оставить в рабочем дереве и перечислить.
3. Написать **передаточный отчёт** `.orca-reports/NN-handoff-<тема>.md` по шаблону `report.md`: что сделано
   (коммиты), что в процессе (файлы, последняя гипотеза, команда воспроизведения), что дальше (следующий шаг
   одной фразой), какие решения уже приняты и почему.
4. Продолжить в **свежей сессии**, которой на вход даются `AGENTS.md`, задача и передаточный отчёт, а не история чата.

Чтобы не дойти до предела, большие дампы не выводят в чат целиком: сначала `jq`, `head` или подсчёт, потом точечное чтение.

## Перенос процесса на новый сервис

Копируются `AGENTS.md`, `CLAUDE.md` (симлинк), `CONTRIBUTING.md`, `docs/roles/`, `docs/templates/` и, если
используются, обёртки агентов (`.claude/agents/`, `.opencode/agent/`). Заменяются имя проекта, путь учётных
данных `~/.<проект>/`, переменные `<PROJECT>_*`, таблица команд и раздел «Структура» в `AGENTS.md`, лимиты
частоты (их определяет разведка). Типичные ошибки в фазах оставляются: они описывают класс проблем,
а не конкретный сайт.
